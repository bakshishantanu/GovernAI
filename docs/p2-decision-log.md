## Foundational tech choices, and why

| Choice | Why |
|---|---|
| **Groq as primary LLM provider, Gemini as fallback** | Both behind a shared `LLMProvider` ABC (Contract 6) so the rest of the system never depends on a specific vendor. Provider-agnostic from day one. |
| **`llama-3.3-70b-versatile` → `openai/gpt-oss-20b`** | The original default model was retired by Groq mid-project. Caught by checking Groq's live `/models` endpoint, not by a failure in production — confirmed working with a real API call before switching. |
| **Circuit breaker + retry/fallback (not just retry)** | FRD-06's exception flow requires that an LLM failure doesn't just retry forever — it retries with backoff on the same provider, then falls back to the next provider, and only then fails the execution gracefully. Per-provider CLOSED/OPEN/HALF_OPEN state avoids hammering a provider that's already down. |
| **Mock adapters for Ticketing and SQL Query, kept mocked permanently** | Deliberate MVP scope, not a shortcut — `TicketingAdapter`/`SqlDataAdapter` are built behind an interface so a real integration (Zendesk, Jira, a real Postgres) could replace them without the skill's tools changing at all, but the plan's own Mock/Stub Strategy always intended these to stay mocked through the demo. |
| **`sqlglot` AST validation for the SQL Query skill (not a regex/keyword blocklist)** | Resolves the open question in PRD.md §11. A regex approach is bypassable; parsing to an AST lets validation confirm read-only (no INSERT/UPDATE/DELETE/DDL) and in-scope tables structurally. Two real bypasses were caught and fixed during implementation: `sqlglot.parse_one()` silently accepting multi-statement input, and CTE aliases being misidentified as out-of-scope tables. Execution also goes through a genuinely read-only DB connection as an independent second layer beneath validation — belt and suspenders, not validation alone. |
| **TF-IDF cosine-similarity retrieval for RAG, not a real embedding model (yet)** | Gemini's embedding quota was blocked on the available account at the time. TF-IDF is a real, swappable-later retrieval implementation — consistent with the same mock-adapter pattern as Ticketing/SQL Query — not a fake stand-in. The real upgrade path already exists: P3's `documents`/`document_chunks` schema already has a pgvector `embedding` column waiting for it. |
| **Access-scope filtering happens BEFORE ranking, never after** | FRD-08 hard requirement. If filtering happened after ranking, a highly-relevant-but-out-of-scope chunk could still leak into "top N, then filtered" logic bugs. Filtering first means an out-of-scope document literally cannot be seen by the scoring step. Verified with a real Groq run: an out-of-scope question about confidential salary data correctly returned zero results, and the LLM honestly reported not finding anything rather than fabricating an answer. |
| **Governance (PolicyEngine) checked inline in `tools_node`, not as an external wrapper** | The original contract (Contract 4) envisioned P1 handing P2 a `govern_tool()` wrapper function. In practice the policy check ended up inline inside `agent_graph.py`'s `tools_node`, calling `PolicyEngine.evaluate()` directly per tool call before executing it — denied calls return the denial reason to the LLM instead of crashing the run. |
| **`max_steps` guard on the reasoning loop** | Prevents a runaway/excessive-agency loop from running forever — a hard requirement from FRD-06, not an afterthought. |

## Features built (solely, by P2)

- **`LLMProvider` / `BaseSkill` ABCs** — the two foundational interfaces (Contracts 5 & 6) everything else in P2's lane is built on.
- **`GroqProvider` and `GeminiProvider`** — both LLM provider implementations.
- **Circuit breaker + `LLMService`** — the resilience layer (retry, exponential backoff, provider fallback).
- **Ticketing skill** (`read_ticket`, `search_tickets`, `create_ticket_reply`) + its mock adapter.
- **SQL Query skill** — AST validator (`validator.py`), read-only seeded adapter (`adapter.py`), the skill/tool itself, and the manual verification script. Built via the full spec-kit pipeline (`specs/001-sql-query-safety/`: spec → plan → tasks → implement).
- **Document Search (RAG) skill** — TF-IDF retrieval (`retrieval.py`), citation-grounding verification (`citations.py`), and the skill/tools with per-scope permission enforcement.
- **LangGraph agent reasoning loop** (`agent_graph.py`'s original `build_agent_graph`/`run_agent`) — the FRD-06 loop itself, plus the `max_steps` guard.
- **`SkillRegistry` bug fixes** — a hardcoded `skill_id="ticketing"` existence check that silently skipped every other skill, missing `required_permission` values on every tool, and `SkillPermission` rows never being persisted despite the table existing for exactly that. Three real bugs, three regression tests, caught by actually reading what the registry produced rather than trusting it compiled.
- **Agent-skill wiring into LangGraph** (`AgentRepository.list_skill_ids`, `SkillRegistry.get_tools`, `runtime/agent_loader.load_agent_tools`) — turns an agent's bound skills into the tool list `build_agent_graph` needs, closing the gap between the skill registry and a runnable agent.

- **Decision: build it at a new route (`/landing`) inside the existing `frontend` app, not a separate app and not replacing the current root (`/`).** The current `(console)/page.tsx` already owns `/` as the live dashboard teammates rely on; two `page.tsx` files can't resolve the same route anyway. `/landing` is reachable for review without touching anything console-side, and `middleware.ts`'s `updateSession` only redirects when `REQUIRE_AUTH === "true"` (unset locally), so the route isn't gated behind auth during review.
- **Decision: scope the new palette to a `.landing` class + its own `landing.css`, not `globals.css`.** Keeps the shadcn/console theme tokens (`--background`, `--primary`, etc.) untouched — this is an experiment sitting next to the real app, not a reskin of it.
- **Palette chosen**: warm cream (`#FAF4E9`/`#F1E8D8`) body sections lifted from Aardvark's editorial off-white, bookended by dark navy (`#0B0C10`/`#12141A`) hero/CTA sections for monday.com/shader.se's professional-dark register, with a terracotta-orange primary accent (`#DE6A34`, Aardvark's "eyecatcher" color) and a teal secondary (`#1F8A83`, also from Aardvark's book-cover palette). The light-to-dark-to-light-to-dark section rhythm itself (not just color choice) is the "dynamic, not static" answer to the brief.
- **Added `framer-motion`** (new dependency, this branch only) — used for `whileInView` reveal-on-scroll (Problem/Features/Personas sections, Aardvark-style), and `useScroll`/`useTransform`/`useMotionValueEvent` for two genuinely scroll-driven pieces modeled on shader.se: a parallax gradient-blob hero, and a pinned "How it works" section (4 steps, `100vh` each, sticky viewport) where the right-hand visual crossfades per step as the user scrolls through it rather than four static screens.
- **Content mapped directly from `PRD.md`** (tagline, problem statement §2, six MVP capabilities §7.1, three personas §4, and the live-cost-governance USP §6) rather than invented copy, so the page actually explains what the product is, not just how it looks.
